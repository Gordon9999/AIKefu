AI客服Agent的三大工程：Intercom与Decagon拆解

以"退票"为例，拆解 Prompt / Context / Harness 三层工程如何驱动 AI 客服，以及 Intercom Fin AI 与 Decagon 的差异在哪、谁在什么场景下赢。

用户说了一句"我有事去不了了，要退票"。

背后是三大工程、十几个模块、两三次 LLM 调用在协作。

这篇文章把整个过程拆开讲清楚。


以 Intercom Fin AI 和 Decagon 两个产品为例。先讲 Fin AI 怎么实现，再讲 Decagon 有什么不同。

一、三大工程是什么

Agent 编程领域有三层工程准备。每一层干不同的活。

工程 干什么 类比
Prompt Engineering 给 LLM 写说明书 员工手册
Context Engineering 给 LLM 塞资料夹 工位上的文件
Harness Engineering 给 LLM 装操作系统 车间控制室

三者不是并列的功能。是一次 LLM 调用之前的三层准备。

二、Fin AI 的模块拆解

以退票场景为例。用户说"我有事去不了了，要退票"。

Harness 层：编排控制

意图路由：判断这是退款意图，走 Custom Answer"退票流程"。

工具编排：查订单时调 API，用户确认后调退款 API。

护栏：退款金额超阈值？用户情绪激动？转人工。


Harness 不生成回复。它控制流程——像状态机，每步决定下一步往哪走。

Context 层：上下文组装

知识 RAG：向量检索"退票政策"，命中"3 天内退 50%"。

对话记忆：管理历史轮次，第 2 轮才说退票也有上下文。

客户数据：查 CRM，查订单系统，拿到 #12345 ¥580。


Context 不决定说什么。它决定LLM 这一轮能看到什么。


核心挑战：1000 篇文章只能塞 3 篇。哪 3 篇最相关？对话超 10 轮怎么压缩？什么时候查订单？

Prompt 层：提示词组装

系统提示词：你是 XX 票务客服，不确定就转人工。

响应模板：Custom Answer 里写好的退票流程骨架。

语气指令：友好、专业、简洁。


Prompt 不做决策。它把所有材料排版成 LLM 最容易理解的格式。

三、Admin 配置什么

Fin AI 的核心理念：让非技术人员配置。Admin 在后台设 5 类东西。

5 类配置

1. 知识库文章：写退票政策 FAQ，会被向量化供检索。

2. Custom Answer：写退票流程骨架。不是死流程，是带条件的建议路径。LLM 会参考但可灵活变通。

3. Agent 人格：选语气，写品牌话术约束。

4. API 工具：注册退款接口，定义参数和返回格式。用 function calling 调。

5. 转接规则：退款超 ¥1000 转人工。连续 3 次不满转人工。API 失败转人工。


用户配的是"材料"和"规则"，不是代码。

四、退票对话走一遍
Turn 1：用户发起退票

用户说："我有事去不了了，要退票"


Harness 接收。意图路由判断 = 退款意图。匹配到 Custom Answer"退票流程"。护栏检查：可以继续。


Context 并行检索。RAG 命中"3 天内退 50%"。查 CRM 拿到 #12345 ¥580。首轮无历史。


Prompt 组装。系统提示词 + 模板 + 知识 + 订单数据 + 用户消息，拼成完整 prompt。


LLM 返回：

"我来帮您处理退票。您的订单 #12345（演唱会票 ¥580），距演出 3 天可退 50% 即 ¥290。确认退票吗？"

Harness 后处理。检查合规，推送给用户。

Turn 2：用户确认

用户说："是的，确认退票"


Harness 判断这是确认执行。调退款 API：refund(order_id="12345", amount=290)。返回成功。


Context 记录 Turn 1，无需重新检索。


LLM 返回：

"退款已成功！¥290 将在 1-3 个工作日内退回。还有其他可以帮您的吗？"
五、三层的关系：不是串行，是嵌套

Harness 是外层循环。每轮决定走什么流程。

需要知识就触发 Context 检索。需要回复就触发 Prompt 组装。需要转人就转。


Harness 调度 Context，Context 喂给 Prompt，Prompt 驱动 LLM，Harness 检查输出。


整个对话是多轮循环。不是一次调用就结束。

六、架构相同，竞争在哪

两个产品都有这三层。有厨房不等于菜好吃。

维度一：每层做多深
能力 一般产品 优秀产品
多步推理 一步查一个 链式：查A→根据A查B→调C
RAG 准确率 10 篇中 3 篇相关 5 篇中 4 篇相关
长对话记忆 超 10 轮就忘 20 轮还记得订单号
Function calling 准确率 85% 99% + 重试 + 降级

85% 和 99% 差 14 个点。放到每天 10 万次对话里，就是14000 次退款失败的差距。

维度二：层间接缝

三层不是独立模块。协作质量决定整体效果。


Harness ↔ Context：用户说"好的"不需要检索。用户说"那退吧"需要查订单但不需要检索知识。少一次 RAG = 少 200ms 延迟。


Prompt ↔ Harness：LLM 幻觉说"全额退款"。Harness 对比知识库发现政策是退 50%。拦截，重新生成。这层检查是安全关键。

维度三：工程之外

Admin UX：5 分钟配好 vs 2 天开发。决定谁能拿到非技术客户。

数据飞轮：100 万次对话 vs 1 万次。架构可以抄，数据不能抄。

生态集成：预置集成多 = 切换成本高 = 客户留存。

成本效率：多模型路由 vs 单模型。决定定价空间。

七、Decagon 的差异：同骨架，不同肌肉

Decagon 架构本质上也是三层。差异在每层做得多深。

Harness 层：三个关键差异

1. AOP vs Custom Answer

Fin AI 的 Custom Answer 是对话模板。LLM 参考它生成回复，但也负责算退款金额。幻觉了就出错。

Decagon 的 AOP 是自然语言写的可执行程序。退款金额用代码算，不是 LLM 算。LLM 只负责把数字说出来。


Fin AI: LLM 算 ¥580 × 50% = ¥290 → 可能算错
Decagon: 代码算 ¥580 × 50% = ¥290 → 不会错

把"不能错"的部分从 LLM 手里拿走。这就是代码级护栏。


2. 多 Agent vs 单 Agent

Fin AI 基本是单 Agent，一个 LLM 调用处理一切。

Decagon 分工：意图识别用小模型，知识检索用专用 Agent，回复生成用大模型，情绪检测独立跑。


3. Supervisor model

Fin AI 生成后做基础护栏检查。Decagon 用独立 LLM 审查另一个 LLM 的输出。第二道防线。

Context 层：两个关键差异

1. 统一知识图谱 vs 基础 RAG

Fin AI 检索帮助中心文章。Decagon 关联帮助文档 + 历史工单 + 实时数据。


用户说"上次你们给我退了，这次怎么不行？"

Fin AI 按当前政策回复，不知用户上次退过。

Decagon 查到上次是 7 天前退的（全额），这次 3 天内（50%）。回复有理有据。


2. 多模型自动路由

Fin AI 所有步骤用一个大模型。意图分类也用 GPT-4，贵且慢。

Decagon 意图分类用小模型 $0.001，生成用大模型 $0.02。每轮省 30%。每天 10 万次省 $900。

Prompt 层：情绪自适应

Fin AI 语气是静态的。不管用户什么情绪都一个调。

Decagon 检测到用户愤怒，动态调整语气："非常抱歉，我立刻为您处理。"

八、谁在什么场景下赢
80% 的简单 case：Fin AI 够用
场景 Fin AI 能不能搞定
信息查询：退票政策是什么 完全够
简单流程：帮我退票 够用
路由分流：转人工 够用
FAQ：营业时间 完全够

这些场景的共同特点：单轮或两轮解决，不需要复杂推理链。

15% 的复杂 case：Decagon 拉开差距

跨系统关联："上次退错了钱"——Fin AI 不知上次记录，Decagon 知识图谱能查到。

确定性推理："退 2 张留 1 张"——Fin AI 用 LLM 算可能错，Decagon 用代码算不会错。

情绪敏感："第三次了！！"——Fin AI 正常语气回复，Decagon 调整语气并加速转人工。

历史回溯："按上次方案处理"——Fin AI 重新问，Decagon 直接执行。

OTA 等高客单价行业：80% 法则

OTA 的特殊性：一个 case 交易金额几百到几万。但一个错误 case 的赔偿成本是交易金额的几倍。


人工处理一个复杂 case 成本 ¥8。AI 出错后的修复成本可能是 ¥500-5000。

那 15% 复杂 case 的自动化收益，不足以覆盖出错的风险成本。


不如直接转人工。快、准、安全。


对 OTA 来说，真正的竞争焦点不是"谁能处理更多 case"。是谁能在 80% 简单 case 上做到更低成本 + 更好体验 + 更丝滑的转人工。


这个方向上，Fin AI 的性价比更高。

九、总结

架构是入场券，不是护城河。


Intercom Fin AI 和 Decagon 都用三层架构。差异在于：

1. 每层执行深度——同样叫 RAG，准确率差 20 个点。

2. 层间接缝——Harness 能不能智能决定"这轮不检索"。

3. Admin UX——5 分钟配好 vs 2 天开发。

4. 数据飞轮——100 万次对话 vs 1 万次。这是最难追的壁垒。


Decagon 在工程深度上全面领先。Fin AI 在配置体验和生态成熟度上有优势。


但对 80% 的自动化客服场景来说，Fin AI 够用了。真正的竞争焦点是简单 case 的成本和体验，以及转人工的衔接质量。
